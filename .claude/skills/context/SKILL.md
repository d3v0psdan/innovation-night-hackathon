# Context

Daniel works best with small, clear steps. One thing at a time, no walls of text.

## First run (challenge just pasted)

1. Read the challenge. Pull out
   - What they literally asked for
   - How it's judged, word for word
   - Any must-haves (provided API, required features, deadlines)
2. Write `CONTEXT.md`, max 40 lines
   - **The ask** one sentence in plain words
   - **Judges care about** the criteria as a short list
   - **Steps** a checklist in priority order, grouped as
     - **Must** without these we have nothing to demo
     - **Should** makes it good
     - **Could** only if time's left
   - Each step is one action, doable in 15 to 30 min, starts with a verb, and names the skill to use (like "Build the question screen with `/design-screen`")
   - Add a rough time next to each step and a running total. Must steps fit in 2 hours max
3. Reply with only the ask, the judges list, and the **first step**. Don't dump the whole list on screen.

## Every run after (what's next)

1. Read `CONTEXT.md`, tick off anything done (check git and the code, don't guess)
2. Check the clock. If behind, move the lowest Should steps to Could and say so in one line
3. Reply with the **one next step** and how long it should take

## Rules
- Priority comes from the judging criteria, not from what's fun to build
- A working demo beats a pretty half-feature, so the end-to-end flow is always the first Must
- `/demo-seed` and `/pitch-prep` are always Must, scheduled for the last 40 minutes
- Never more than 3 lines of reply unless Daniel asks for more
